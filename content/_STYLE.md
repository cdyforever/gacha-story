# 深度解读写作规范（content/_STYLE.md）

> 这份文档定义「逐幕解读」的文体标准。目标是把全站每幕的正文汉字数
> **从现状中位数 250 字提升到 800–1200 字**，且增量全部落在「解读」而非「复述」上。
>
> 配套工具：`python tools/stats.py`（随时体检字数与分布）

---

## 一、核心区别：复述 vs 解读

| | 复述 Synopsis | 解读 Analysis |
|---|---|---|
| 回答的问题 | 发生了什么 | **为什么这样写、意味着什么** |
| 读者的收获 | 知道剧情 | 理解结构、看懂手法 |
| 典型句式 | 「XX 在这里击败了 YY」 | 「这场战斗被安排在第三章，是因为……」 |
| 可否被剧透替代 | 可以（看剧透就够了） | **不可以（这才是本站的价值）** |

**判断标准**：如果这段话删掉后读者只是「少知道一点剧情」，那是复述；
如果删掉后读者「少看懂一层」，那才是解读。

现状问题：全站解读性词汇（主题/象征/伏笔/隐喻/呼应/动机…）平均每页仅出现 3 次。
这个数字应该提高到每页 15–25 次。

---

## 二、六问模板（每幕必答）

动笔前先回答这六个问题，再组织成文。**1 是旧内容，2–6 是新增。**

| # | 问题 | 篇幅建议 | 常见写法 |
|---|---|---|---|
| 1 | 发生了什么 | 25–30% | 保留现有梗概写法，压缩到最精炼 |
| 2 | **为什么这样写** | 15–20% | 叙事意图、结构安排、节奏设计 |
| 3 | **伏笔与回收** | 15–20% | 这里埋了什么，在哪一幕回收 |
| 4 | **角色弧光** | 15% | 这个角色的动机如何变化 |
| 5 | **主题与象征** | 15% | 母题、意象、呼应关系 |
| 6 | **争议与多解** | 5–10% | 玩家分歧、开放性解读 |

不要求每幕六问全满。**但 2、3、5 三项必须至少出现一项**，否则这一幕就还是复述。

## 三、块指令用法

### `::: scene` — 名场面（解读的锚点）

用具体对白把抽象解读钉在读者能记住的画面上。

```
::: scene 名场面 · 标题（一句话点出这一幕的核心矛盾）
> 对白原文第一句。
> 对白原文第二句。
> —— 说话人 · 出处

点评第一段：这句话为什么重要。

点评第二段：它在整幕/全篇中的位置。
[直达按钮 P5|5]
:::
```

规则：
- `>` 开头是对白，`> ——` 开头是署名
- 空行分段，每段渲染为一个 `<p>`
- 末尾可加 `[按钮文字|分P号]`
- **每幕配 0–2 个 scene 块**，不要滥用；只在「这一幕最有力的那句话」处使用

### `::: deep` — 补充资料（默认折叠）

核心解读应直接写入正文或使用 `::: insight`，不要把本站最有价值的内容全部藏起来。`deep` 只承载不影响主线理解的扩展资料。

```
::: deep 深度解读 · 3.0 为什么必须这么慢 {light}
### 小标题一
正文段落。

### 小标题二
正文段落。

- 列表项
- 列表项
:::
```

规则：
- 标题行末尾的 `{light|mid|heavy}` 可选，标记剧透级别
- 内部支持 `###` 小标题、`-` 列表、普通段落
- 折叠标题以 `💡` 开头渲染
- **补充资料与正文分离**——复述与核心解读留在正文，扩展资料才进 deep 块

### 其他可用块

| 块 | 用途 |
|---|---|
| `::: note` | 提示框，**会终止当前幕**（写在幕末） |
| `::: pbtns` | 分P直达按钮组，幕内使用 |
| `::: reveal` | 红级剧透遮挡区（用于主题区总结） |
| `::: personas` | 人物志卡片（见人物志章节） |
| `::: cards2` | 双列卡片 |

> ⚠️ `note` 写在幕中间会提前关闭该幕卡片；`scene` / `deep` / `pbtns` 则安全地留在幕内。

## 四、写作要求（质量红线）

**要做的**
- 用**具体细节**支撑观点。不要写「这段很感人」，要写「他停顿了三次才说出这个名字」。
- 敢于下判断，但标明这是**一种视角**。用「本页认为」「一种读法是」，而非「正确解读是」。
- 建立**跨幕连接**。第 3 幕的伏笔要在第 8 幕被回收——这是本站相对单集视频解说的独特优势。
- 引用**原文对白**。本站素材库（`_raw/`）含任务原文；不足时须补充可靠出处，不得把任务流程当作完整台词。

**不要做的**
- ❌ 把梗概拉长冒充解读（灌水式扩写）
- ❌ 通篇抽象术语（「命运的能指」「主体的消解」）而无具体例证
- ❌ 剧透失控。解读涉及后幕内容时，用 `::: reveal` 或 `::: deep {heavy}` 包裹
- ❌ 复述游戏流程（「点击这里」「打败这个怪」）

## 五、执行顺序（推荐）

1. **先做样板幕**：挑素材最全的一幕（如原神枫丹「审判日」、星铁 3.0），写到 1100+ 字，人工审定
2. **审定通过后**，把写法固化为本文件的案例
3. **按页批量补齐**，从最薄的开始：

| 优先级 | 页面 | 当前每幕均字 |
|---|---|---|
| 1 | genshin-luna | 224 |
| 2 | fgo-eor | 265 |
| 3 | genshin-natlan | 278 |
| 4 | fgo-part1 | 294 |
| 5 | hsr-amphoreus | 429（★ 3.0 已做样板） |

4. 每补完一页跑一次 `python tools/stats.py` 记录进展
5. 全部补齐后再考虑动 `genshin-interludes`（该页 0 幕，结构特殊，需单独处理）

## 六、验收标准

单幕合格线：

- [ ] 正文汉字 ≥ 800
- [ ] 六问中至少覆盖 2、3、5 里的一项
- [ ] 至少 1 处引用原文对白（`::: scene`）
- [ ] 至少 1 处跨幕/跨章呼应
- [ ] 核心解读默认展开，可用 `::: insight`；只有补充资料才用 `::: deep` 折叠

全站合格线：每幕均字 ≥ 800，中位数 ≥ 700。
（2026-09 基线：均字 441，中位数 250）
